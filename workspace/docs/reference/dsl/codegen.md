# DSL Codegen Contract

This page records the compiled output that the `dotzuki-engine-dsl` compiler
emits for every Game DSL construct — JavaScript for `.scene` storylines, JSON
for UI layouts, themes, styles, and atlases — settled against the compiler
source in `crates/dotzuki-engine-dsl/src/`.

> - **Audience**: DSL authors, compiler maintainers
> - **Type**: reference
> - **Status**: active
> - **Last verified**: v0.1.0

## How to read this page

- Every behavioral claim carries a `path:line` citation into
  `crates/dotzuki-engine-dsl/src/`.
- This page replaces the legacy `DSL_MAPPING.md` and reconciles it with the
  archived design record at [dsl-unified-design.md](../../archive/dsl-unified-design.md).
  Where the two disagreed, the compiler source decides (doc-standard §11:
  code wins over docs).
- Syntax and grammar details live in the sibling pages: `.scene` statements
  in [scene.md](scene.md), UI components in [gui.md](gui.md) (formerly
  `GAME_UI_DSL.md`), theme/style in [theme-style.md](theme-style.md)
  (formerly `THEME_STYLE_DSL.md`).
- The `.scene` runtime binding contract (`script_config.json`) is described
  in [project-manifest.md](../project-manifest.md) (formerly
  `game-project-spec.md`).
- The docs index ([README.md](../../README.md)) lists this page's place in
  the reference layer.

Every example below compiles under the current compiler; the full
`dotzuki-engine-dsl` test suite is green (lib 279, codegen 34, snapshots 8,
integration 18, and the remaining suites), and the divergent shapes were
confirmed by compiling the examples directly.

## Compilation pipeline

- Four file extensions: `.scene`, `.gui`, `.theme`, `.style`
  (compiler.rs:74).
- `.theme` and `.style` file contents are wrapped in
  `game_scene _auto { ... }` before parsing, so their blocks parse as scene
  directives (compiler.rs:199-205).
- Pipeline: lex → parse → semantic validation → codegen
  (compiler.rs:199-231).
- Semantic validation rejects: undefined variables in conditions,
  assignments, and speaker names; empty `@choice`; missing or circular
  `@style` parents; duplicate `@theme`/`@style` names (parser.rs:1728-1905).

Artifacts written by the build-time compiler (compiler.rs:291-343):

| Source | Artifacts |
|---|---|
| `.scene` | `<Scene>.js`; `<Scene>_ui.json` when a `ui` block exists; `<Scene>_theme_<i>.json` per `@theme`; `<Scene>_styles.json` when `@style` blocks exist; `<Scene>_atlas_<i>.json` per `@atlas` |
| `.gui` | `<Screen>.json` |
| `.theme` | `<ThemeName>.json` per `@theme` block |
| `.style` | `<Scene>_styles.json` — the wrapper scene name is `_auto`, so a standalone `.style` file writes `_auto_styles.json` |

- Build-time artifacts start with
  `// @generated by dotzuki-engine-dsl — do not edit.` and
  `// Source: <path>` (compiler.rs:240-241, 301-304).
- The `.js` artifact ends with an inline base64 `//# sourceMappingURL`
  (compiler.rs:288-289).
- Artifacts are rewritten only when their content changed
  (`write_if_changed`, compiler.rs:617-635).

## Two execution targets

The crate emits JS, and it also ships a native AST interpreter that executes
`.scene` ASTs with no JS engine at all:

- The interpreter is the canonical scene semantics; the compiled-JS path
  (the `dotzuki-engine-script` Boa engine) is the fallback
  (interpreter.rs:1-24).
- Statements the interpreter rejects are marked in each section below.

## Scene module shape

`game_scene <Name> { ... }` compiles to one JS module in this order
(compiler.rs:234-289):

1. `@variables` declarations first — one `let <name> = <value>;` per
   declaration (js_variables.rs:21-46).
2. One `export async function storyline_<name>() { ... }` per
   `@storyline("name")` block, in declaration order (compiler.rs:257-280).
   The legacy unnamed `@storylines { ... }` block becomes
   `storyline_main()` and carries no trigger bindings
   (parser.rs:684-692, js_storyline.rs:494-502).
3. `export async function <SceneName>OnLoad() { ... }` when a `@load` block
   exists (js_storyline.rs:504-511).

## Storyline statements

Statement forms valid in `@storyline`/`@storylines`/`@load` bodies and inside
`@if`, `@choice`, and `@each` branches (parser.rs:1011-1034).

### `@speaker` / `@say`

```dsl
@speaker("Prof") {
    "Hello! Welcome to the world of monsters!"
}
```

compiles to (js_storyline.rs:197-259):

```js
await game.showText("Prof: Hello! Welcome to the world of monsters!");
```

- A non-empty string-literal name is prepended as `"Name: "` inside the
  emitted string.
- `@speaker("")` is the narrator form: the body is emitted verbatim with no
  prefix (js_storyline.rs:217-223). Regression test
  `test_speaker_empty_name_no_prefix` (js_storyline.rs:633-652).
- A variable name compiles to a template literal: `` `${name}: text` ``
  (js_storyline.rs:225-228).
- Multiple text lines inside one block are joined with `\n`
  (js_storyline.rs:212).
- `@speaker` and `@say` emit identical JS; they differ in meaning —
  `@speaker` is player-initiated talk, `@say` is cutscene speech
  (ast.rs:221-230, js_storyline.rs:184-196).
- Localized `@t(...)` lines compile through `game.t("en", "zh")`
  (js_storyline.rs:229-254).

### `@choice` / `@option`

```dsl
@choice {
    @option("Yes") {
        @speaker("Prof") { "Great!" }
    }
    @option("No") {
        @speaker("Prof") { "Too bad." }
    }
}
```

compiles to (js_storyline.rs:266-319):

```js
const choice = await game.showChoice(["Yes", "No"]);
if (choice === 0) {
    await game.showText("Prof: Great!");
} else {
    await game.showText("Prof: Too bad.");
}
```

- The last option is the `else` branch; every earlier option gets
  `if (choice === N)` or `else if (choice === N)`
  (js_storyline.rs:297-305).

### `@if` / `@else` — condition compilation (settled)

DSL conditions are expression ASTs compiled by `compile_expression`
(js_storyline.rs:76-140) and wrapped by `compile_if`
(js_storyline.rs:322-363). These facts contradict legacy `DSL_MAPPING.md`
§3 and entry 4:

- `@if (gold > 100) { ... } @else { ... }` compiles to:

```js
if ((gold > 100)) {
    ...
} else {
    ...
}
```

- The condition is parenthesized twice: `compile_expression` wraps every
  binary operation in `(...)` and `compile_if` emits `if ({cond})`
  (js_storyline.rs:120, 338).
- `==` in DSL compiles to `===` in JS (js_storyline.rs:37). The interpreter
  also uses strict equality (interpreter.rs:111-119).
- Bare call callees in conditions are namespaced to `game.`:
  `@if (getFlag("EVENT_X"))` compiles to
  `if (game.getFlag("EVENT_X"))` (js_storyline.rs:99-108; regression test
  `test_condition_calls_are_game_namespaced`, tests/codegen_tests.rs:954-978).
- Undefined variable names are NOT resolved through `game.getFlag()`. They
  fail semantic validation at compile time with `UndefinedVariable`
  (parser.rs:1791-1798). The legacy claim that "undefined names that match
  known flags compile to `game.getFlag()`" does not exist in the code.
- Else-if chains are written `@else @if (...) { ... }`. The parser
  desugars them to a nested `If` inside the else branch
  (parser.rs:1134-1173), so the JS is nested, not a flat `else if` chain:

```dsl
@if (gold > 100) {
    @speaker("") { "rich" }
} @else @if (gold > 10) {
    @speaker("") { "mid" }
} @else {
    @speaker("") { "poor" }
}
```

```js
if ((gold > 100)) {
    await game.showText("rich");
} else {
    if ((gold > 10)) {
        await game.showText("mid");
    } else {
        await game.showText("poor");
    }
}
```

- Spelling `@else if` (no `@` on `if`) is a parse error:
  `expected one of [LBrace], found Identifier("if")`.
- In the native interpreter an `@if` condition must evaluate through sync
  queries only; an async command in a condition is an error
  (interpreter.rs:459-473).

### `@each`

```dsl
@each item in inventory {
    @speaker("") { "..." }
}
```

compiles to `for (const item of inventory) { ... }`
(js_storyline.rs:366-396). The `in` keyword is optional
(parser.rs:1189-1197).

### Assignment statements

- `gold = 500` compiles to a bare `gold = 500;`. The `let gold = 500;`
  declaration is hoisted to the top of the storyline function
  (js_storyline.rs:398-428, 531-576).
- Assignments whose value is a call stay in place and are awaited:
  `result = startBattle("OPP")` compiles to
  `result = await game.startBattle("OPP");` with a hoisted `let result;`
  (js_storyline.rs:409-418, 557-571).
- Assigning to a `@variables` name mutates the module-scoped variable; no
  local `let` is emitted (js_storyline.rs:543-554).

### Bare commands and `@command`

```dsl
heal()
giveItem("Potion", 1)
fadeScreen("out")
```

compiles to (js_storyline.rs:461-481):

```js
await game["heal"]();
await game["giveItem"]("Potion", 1);
await game["fadeScreen"]("out");
```

- `@command("heal")` and `@command("giveItem", "Potion", 1)` compile
  identically; the first argument must be a string literal
  (parser.rs:1252-1304).
- A bare identifier without parentheses is also a command: `heal` →
  `await game["heal"]();` (parser.rs:1218-1245).
- A bare identifier followed by `=` is an assignment; otherwise it is a
  command (parser.rs:1020-1023).

### `@run { ... }` — raw JavaScript (settled)

The two legacy docs disagree: `DSL_MAPPING.md` entry 14 calls `@run` a
current, first-class escape hatch; the archived design reports all `@run`
blocks were removed from the pokered corpus as an anti-pattern. The
compiler code says:

- `@run { ... }` lexes the block as raw text with brace-nesting awareness
  (lexer.rs:491-543) into `StoryStmt::Run` (parser.rs:988-1009).
- Codegen emits each non-empty line verbatim, prefixed with the compiler's
  indentation pad; the author's inner indentation is preserved; blank lines
  are kept; no sourcemap entries are produced (js_storyline.rs:55-74).
- `@run` is valid anywhere `parse_story_stmt` runs: storyline bodies,
  `@load`, `@if`/`@else` branches, and `@choice` option bodies
  (parser.rs:1011-1034). It is NOT valid at `game_scene` top level
  (parser.rs:679-720).
- The semantic validator skips `@run` content entirely: no
  undefined-variable errors for JS identifiers inside it
  (parser.rs:1774, 1826, 1845).
- The native AST interpreter REJECTS `@run` with an error
  ("unsupported statement: @run raw-JS blocks cannot run in the native
  interpreter", interpreter.rs:524-528).

Net effect: `@run` compiles for the JS/Boa runtime path and is rejected by
the canonical interpreter. Both legacy descriptions are partial; the two
behaviors coexist in the current code.

## `@variables`

```dsl
@variables {
    gold = 500
    player = { name: "RED", level: 5 }
    inventory = ["sword", "shield"]
}
```

compiles to (js_variables.rs:21-46):

```js
let gold = 500;
let player = { name: "RED", level: 5 };
let inventory = ["sword", "shield"];
```

- Object literals use `key: value` (colon). `{ name = "RED" }` is a parse
  error: `expected one of [Colon], found Equals` (parser.rs:424-451).
- There is no `const` form; every declaration is `let`.
- Call initializers are NOT namespaced to `game.`:
  `flag = getFlag("EVENT_X")` compiles to
  `let flag = getFlag("EVENT_X");` (js_variables.rs:93-96) — unlike story
  expressions, which namespace to `game.getFlag(...)`.

## Expressions

`compile_expression` (js_storyline.rs:76-140) maps expression ASTs to JS:

| DSL expression | JS output |
|---|---|
| `"text"` | JSON-escaped string literal |
| `42` / `3.14` | `42` / `3.14` (integers print without `.0`) |
| `true` / `false` | `true` / `false` |
| `gold` | `gold` |
| `[1, 2]` | `[1, 2]` |
| `{ a: 1, b: 2 }` | `{ a: 1, b: 2 }` |
| `getFlag("X")` | `game.getFlag("X")` |
| `!x` / `-x` | `(!x)` / `(-x)` |
| `a + b` (any binop) | `(a + b)` |
| `c ? t : e` | `(c ? t : e)` |

- Operator mapping: `==`→`===`, `!=`→`!==`, `&&`, `||`, `|`, `&`,
  `+ - * / > < >= <=` (js_storyline.rs:31-48).
- Identifiers may contain `.` and `-` (lexer.rs:438-447). A dotted name is
  one identifier, not member access. Writing `game.getFlag("X")` in DSL
  therefore compiles to `game.game.getFlag("X")` — write bare
  `getFlag("X")` instead.
- String interpolation (`{expression}` inside a string) is NOT implemented:
  the lexer reads strings verbatim (lexer.rs:376-400), and no codegen pass
  extracts `{...}` into JS template literals. Legacy `DSL_MAPPING.md`
  entry 6 describes a feature that does not exist in this compiler. What
  exists is the GUI binding convention: a variable used as a UI property
  compiles to the string `"{name}"` for the renderer
  (json_ui.rs:366-385). GUI template bindings use loose `==`/`!=` inside
  the template string (json_ui.rs:493-510), while JS code and the
  interpreter use strict equality.

## UI JSON (`.gui` and `ui { }` blocks)

- `.gui` `screen <Name> { ... }` compiles to
  `{"schema_version": 2, "screen": "<Name>", "elements": [...]}`
  (json_ui.rs:40-49).
- `screen <Name> : <theme>` parses the theme name (parser.rs:735-738) but
  the emitted JSON does not include it (json_ui.rs:40-49).
- A `.scene` `ui { ... }` block compiles to
  `{"type": "group", "children": [...]}` (json_ui.rs:28-35).
- Component mapping (json_ui.rs:52-240):

| DSL component | JSON output |
|---|---|
| `panel { ... }` | `{ "type": "border", "children": [...] }` |
| `container { ... }` | `{ "type": "group", "children": [...] }` |
| `text("Shop") {}` | `{ "type": "text", "value": "Shop" }` |
| `button("Buy") { on_click = "buy" }` | `{ "type": "text", "value": "Buy", "interactive": true, "onClick": "buy" }` |
| `list { source = items }` | `{ "type": "list", "items": "{items}" }` |
| `flex_list(items)` | `{ "type": "flex_list", "items": "{items}" }` |
| `image("ui.png") { slice = "[8,8,8,8]" }` | `{ "type": "image", "src": "ui.png", "nineSlice": "[8,8,8,8]" }` |
| `tile(31) { rect = {...} }` | `{ "type": "tile", "tile_id": 31, "rect": {...} }` |
| `divider { tiles = [122] }` | `{ "type": "divider", "tiles": [122] }` |
| `input` / `dropdown` | `{ "type": "custom:input" }` / `{ "type": "custom:dropdown" }` |
| `cursor` / `bracket` / `pixel_rect` | `{ "type": "cursor" / "bracket" / "pixel_rect" }` |
| declared `component` use | `{ "type": "custom:<name>" }` |

- Every component requires a `{ ... }` block, even when empty
  (`text("Hi") {}`). `text("Hi")` without the block is a parse error.
- A named child `title = text("Shop") {}` carries `"id": "title"`
  (parser.rs:1324-1353, json_ui.rs:246-249).
- Prop name mapping: `on_click` → `onClick`, `flex_grow` → `flexGrow`
  (json_ui.rs:246-267).
- A single numeric `padding = 24` expands to `[24, 24, 24, 24]`; a single
  non-numeric value is kept as a scalar (parser.rs:1464-1470,
  json_ui.rs:351-359).
- Non-string positional arguments to `text()`/`button()` produce an empty
  string (parser.rs:1928-1934).
- Legacy `DSL_MAPPING.md` entries 7/8 show `{"type": "panel"}` and
  `{"type": "button", "label": ...}` — the emitted types are `border` and
  `text` (with `interactive`), as above.

## `@theme`

Full reference in [theme-style.md](theme-style.md). Code facts
(json_theme.rs:9-15, compiler.rs:378-393):

```dsl
@theme dark {
    primary = "#c9a03d"
    background = "#1a1a2e"
}
```

compiles to
`{"name": "dark", "tokens": {"primary": "#c9a03d", "background": "#1a1a2e"}}`.

- Tokens are strings only (parser.rs:1579-1582).
- Each `@theme` writes its own `<ThemeName>.json` file; a `.theme` file
  with several blocks produces several files, not one map (contradicts
  legacy `DSL_MAPPING.md` entry 9).

## `@style`

Full reference in [theme-style.md](theme-style.md). Code facts
(json_theme.rs:45-141):

- Inheritance resolves at compile time. The output is a JSON array of style
  objects, each with `name`, merged `properties` (child overrides parent),
  `extends` when declared, and `inheritance_chain` when the chain has more
  than one member.
- Property values: literals become JSON primitives; a variable becomes
  `{"$var": "<name>"}` (json_theme.rs:132-141).
- Circular inheritance is a compile-time error
  (`CircularStyleInheritance`, parser.rs:1862-1868); a missing parent is
  `MissingStyleParent` (parser.rs:1853-1861).
- The legacy `__extends` field does not exist; the field is `extends`
  (contradicts legacy `DSL_MAPPING.md` entry 10).

## `@atlas`

```dsl
@atlas "ui" {
    source = "assets/ui/atlas.png"
    regions = {
        btn = [0, 0, 64, 64, slice=8]
    }
}
```

compiles to (json_atlas.rs:35-65):

```json
{
  "name": "ui",
  "source": "assets/ui/atlas.png",
  "regions": [
    {
      "name": "btn",
      "x": 0, "y": 0, "w": 64, "h": 64,
      "nineSlice": { "top": 8, "right": 8, "bottom": 8, "left": 8 }
    }
  ]
}
```

- Region keys are `w`/`h`, not `width`/`height` (contradicts legacy
  `DSL_MAPPING.md` entry 11).
- `slice=8` expands to four equal edges; `slice=[top, right, bottom, left]`
  maps each edge (parser.rs:1702-1718). Regions without `slice` omit
  `nineSlice` (json_atlas.rs:56-63).

## Trigger bindings → `script_config.json`

`@trigger` fields in a `@storyline` regenerate the map's
`script_config.json` (config_gen.rs:18-99). The runtime contract is
documented in [project-manifest.md](../project-manifest.md).

- `npc = N` (number or numeric string) → an `npcs[]` entry
  `{ "id": N, "talk": "<storyline>" }`, plus `toggleId`/`scriptId`/
  `defaultHidden` when `toggle`/`script`/`hidden` are given;
  `no_talk = true` omits `talk` (config_gen.rs:28-43). A non-numeric string
  fills the legacy advisory `npc` name field, used for route and conflict
  grouping only (parser.rs:893-900).
- `sign = N` → a `signs[]` entry `{ "id": N, "talk": "<storyline>" }`
  (config_gen.rs:45-47).
- `coord = [x, y]` / `coords = [[x, y], ...]` → `coordEvents[]` entries
  `{ "name": ..., "position": [x, y], "trigger": "<storyline>" }`
  (config_gen.rs:49-72).
- Coord name derivation: the `name` field when there is one coord; with
  several coords the trailing digit is stripped and renumbered
  (`northExit1` → `northExit1`, `northExit2`, ...); unnamed coords get
  `<storyline>_<x>_<y>` (config_gen.rs:50-70).
- Any `@load` block sets `onLoad` to `<SceneName>OnLoad`
  (config_gen.rs:81-83).
- One `@trigger` line per binding; a storyline may carry several
  `@trigger` lines (parser.rs:807-840).
- `after` links storylines for conflict detection: two storylines on the
  same `(map, npc)` without an `after` chain produce a `CONFLICT` warning
  in the compile diagnostics (conflict.rs:16-96). `onEnter`-only routes do
  not participate (conflict.rs:38-44).
- The compiler can also emit an advisory `storyline_routes.json`
  (`{"routes": [...]}`) via `compiler::generate_routing_table`
  (compiler.rs:639-645); runtime routing is driven by `script_config.json`.

## `@t("en", "中文")` i18n

- Locale codes are positional: the first argument is `en`, the second is
  `zh`; extra arguments get `und` (parser.rs:492-526).
- Scene JS: `@t(...)` compiles to `game.t("en", "zh")` (i18n.rs:10-30,
  js_storyline.rs:79).
- GUI JSON: `@t(...)` compiles to `{"en": "...", "zh": "..."}`, resolved
  by the renderer at draw time (json_ui.rs:12-23).

## Native AST interpreter (canonical semantics)

`interpreter.rs` executes `.scene` ASTs directly, mirroring the Boa runtime
protocol 1:1 (interpreter.rs:1-24):

- Supported: `@speaker`/`@say`, `@choice`/`@option`, `@if`/`@else`,
  `@each`, bare commands, assignments.
- Rejected: `@run` (interpreter.rs:524-528), object literals
  (interpreter.rs:670-674), and async commands inside conditions or
  expressions (interpreter.rs:465-472, 543-556).
- A `showChoice` result out of range falls through to the last option
  (interpreter.rs:361-371), matching the JS `else` shape.

## Open questions

- `@run` direction: the compiler and the JS runtime path accept `@run`
  (js_storyline.rs:60-74) while the canonical interpreter rejects it
  (interpreter.rs:524-528). `DSL_MAPPING.md` entry 14 calls it a current,
  first-class escape hatch; the archived design calls it a removed
  anti-pattern. Which behavior is the intended long-term contract is a
  design decision the code does not state.
- `@variables` initializer calls are emitted without the `game.` namespace
  (`let flag = getFlag("EVENT_X");`, js_variables.rs:93-96), unlike story
  expressions (`game.getFlag(...)`, js_storyline.rs:99-108). The semantic
  validator permits call initializers (parser.rs:1741-1751). Whether
  `@variables` initializers may contain calls at all is unsettled.
- Corpus-state claims: the archived design's verification numbers (248
  maps, zero `@run` blocks, 10 maps with un-inlined constants in
  conditions) and `DSL_MAPPING.md`'s config round-trip claims describe the
  pokered game corpus, which lives outside this repository. They cannot be
  checked from this repo.
- `storyline_routes.json` consumers: the compiler can write the file
  (compiler.rs:639-645), and the in-crate conflict detector operates on
  in-memory routes without reading it (conflict.rs:16-96).
  `DSL_MAPPING.md` entry 13 says the JSON powers a build-time conflict
  detector; no caller of `generate_routing_table` exists in this crate, so
  the consumer is unsettled.
