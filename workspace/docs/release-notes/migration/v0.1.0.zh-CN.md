# 迁移指南 — v0.5.x（预发布）→ v0.1.0

如何把游戏仓库从 v0.5.x git tag 时代迁到已发布的 v0.1.0 workspace。

> 本文是 `release-notes/migration/v0.1.0.md` 的中文翻译，同步至引擎版本 v0.1.0（源文档 commit 3133fb419ae3bc6e5c08bbbcd43ac7fa0289e44f）。
> 内容以英文源为准；发现不一致请更新英文源再同步翻译。

> - **Audience**: rust developers
> - **Type**: how-to
> - **Status**: active
> - **Last verified**: v0.1.0

v0.1.0 是引擎 workspace 的第一个 crates.io 版本。它重排了版本线（预发布 tag 是
`v0.5.0` / `v0.5.1`；发布的 workspace 版本是 `0.1.0`）并接入了发布管线——仅此而已。
tag `v0.1.0` 的代码只比 `v0.5.1` 多一个提交：`workspace/crates/*/Cargo.toml` 里的版本
字符串、发布脚本（`workspace/scripts/publish-crates.sh`）和 tag 驱动的发布工作流。
那次跳跃没有改动任何引擎 API，因此本指南没有破坏性变更要描述；它记录真正改变的两件
事：crate 从哪里来，以及版本号意味着什么。

## 之前（v0.5.x 时代）

游戏以 Cargo **git 依赖**的形式消费引擎，固定到预发布 tag：

```toml
[dependencies]
dotzuki-engine = { git = "https://github.com/liuyanghejerry/dotzuki", tag = "v0.5.1" }
dotzuki-rules  = { git = "https://github.com/liuyanghejerry/dotzuki", tag = "v0.5.1" }
```

## 之后（v0.1.0）

同样的 crate，发布到 crates.io。两种形式都仍然支持：

```toml
[dependencies]
# Registry（推荐）：所有 dotzuki-* crate 共享一个版本。
dotzuki-engine = "0.1.0"
dotzuki-rules  = "0.1.0"

# 或者继续固定 git tag。
dotzuki-engine = { git = "https://github.com/liuyanghejerry/dotzuki", tag = "v0.1.0" }
dotzuki-rules  = { git = "https://github.com/liuyanghejerry/dotzuki", tag = "v0.1.0" }
```

### 步骤

1. 把所有 `tag = "v0.5.x"` 换成 `tag = "v0.1.0"`，或者把依赖改成 registry 形式
   `dotzuki-<crate> = "0.1.0"`。
2. 如果你的游戏在仓库里自带一份 workspace 副本，把每个内部 `dotzuki-*` path
   依赖的 `version` 字符串一并升到 `0.1.0`——crates.io 通过 registry 解析 path
   依赖，版本不一致会让发布门禁失败。
3. `cargo update && cargo build`——一次干净的构建就是全部迁移。
4. 使用 `dotzuki new` 项目（零 Rust 游戏）的话什么都不用改：那些项目里没有
   Cargo 清单。

## 自 v0.1.0 起的版本政策

- 单一共享版本：每个 `dotzuki-*` crate 继承 workspace 版本；一次版本号提升发布全部
  crate。
- tag `vX.Y.Z` 会把每个 crate 以 `X.Y.Z` 发布（发布工作流运行
  `workspace/scripts/publish-crates.sh`）。
- 每个版本在本目录附带一篇迁移指南；changelog 在该版本的条目里链接它。
